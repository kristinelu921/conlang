# Launch ELF Training

Launch ELF only through `gcloud compute tpus tpu-vm ssh`. Never execute `train.py` on the current host, even for a smoke test.

## Use the accumulated operational runbook

Before selecting capacity, localizing data or checkpoints, staging source,
launching, evaluating, or recovering a run, read
[`references/operational_lessons.md`](references/operational_lessons.md) in
full. It is the durable fast path and failure-memory companion to this skill.
Apply its exact-checkpoint, topology, locality, integrity, paired-evaluation,
monitoring, and reporting gates in addition to the rules below. When a new
failure or reliable efficiency improvement is discovered, update that reference
and add a focused guidance test in the same change so the lesson survives later
sessions.

## Enforce the ownership allowlist first

Always prefer a TPU whose exact resource name contains `kristine`, case-insensitively. Ordinary launch, resume, relocate, and recovery requests stay on that allowlist: reject a non-`kristine` target before any cloud call, keep rerunning the filtered `check_tpus.sh` inventory, and do not ask the user for a TPU name or provision capacity implicitly. A wide sweep of other TPUs is allowed only when the current message contains the exact phrase `AUTHORIZE WIDE READ-ONLY TPU SWEEP`. That sweep is read-only and exists only to learn which TPUs are not actively held. It is never acceptable to interrupt a run, affect a run, or make yourself known to a run. A later full sweep may read-only re-query a TPU previously found actively held, because its job may have finished and the TPU may be inactive again. Every sweep stays read-only and must never touch an existing active job. On a non-`kristine` TPU, do not edit, stop, or touch an actively held run owned by somebody else at any point, even when the user requests it. A process owned by kristine may be terminated only when the user explicitly authorizes that termination, and never as part of a sweep. If a run is owned by somebody else on a non-`kristine` TPU, never edit, stop, touch, or interrupt it. On a `kristine` TPU, the documented recovery rules apply. Acquiring an idle non-`kristine` TPU requires the later exact phrase `AUTHORIZE IDLE NON-KRISTINE TPU ACQUISITION` naming that TPU, and only after the read shows it is not actively held. Idle, READY, same-project, or accessible status does not itself authorize inspection or use.

## Select the optimal authorized TPU

Whenever the user asks to launch, resume, relocate, or update a run, first run `ELF_TPU_INITIALIZE_MISSING=0 bash tpu_scripts/check_tpus.sh he-vision-group`. Select only from its final `AVAILABLE` table and only an exact `kristine` resource, unless the current message contains the TPU Ownership Safeguard key phrases for a read-only sweep and a later idle acquisition. Choose the most efficient compatible TPU from that table using validated examples/second, sufficient HBM headroom, topology/compilation compatibility, and the availability of region-local checkpoint and data sources; never choose solely by accelerator count. Initialize and occupancy-check only the selected candidate. Never invoke `tpu_scripts/query_tpus.sh` unless the user explicitly requests new TPU provisioning in the current conversation; an ordinary launch or recovery request is not provisioning authority.

## Never reboot a TPU

Never reboot, reset, or restart a TPU VM or its guest OS under any circumstances, even when a user requests or authorizes it. Do not run guest commands such as `reboot`, `shutdown -r`, or `systemctl reboot`; do not invoke a cloud API or CLI reset/restart operation; and do not stop then start a TPU as a reboot workaround. When a training process is kernel-stuck, leave the TPU untouched, record the failed or interrupted run, and move only to a separately authorized non-reboot recovery path or another authorized `kristine` TPU.

## Establish the run

Record the project, TPU name and zone, config, epoch count, seed, dataset source, node-local dataset path, node-local output path, optional artifact bucket, and exact command. Reject a TPU name that does not contain `kristine` unless the current message contains `AUTHORIZE IDLE NON-KRISTINE TPU ACQUISITION` for that exact name after `AUTHORIZE WIDE READ-ONLY TPU SWEEP` showed it is not actively held. Use the repository's `query-monitor-gcp-tpus` skill. The default sweep verifies the node through a server-side `kristine` name filter.

Before staging, commit and push only the smallest reproducible configuration
closure for the selected run. Normally commit one primary run YAML: the exact
file passed to the launcher and later linked to the launched, fully monitored
run. Add a referenced sampling or secondary config only when the primary YAML
requires that exact version and it is not already committed. Never bulk-stage a
configuration directory, stage by YAML extension, or sweep all modified and
untracked YAMLs into the run's commit. Exclude unrelated, abandoned, superseded,
and speculative candidate configs. Add a retry config only when selecting it for
immediate launch under its own run identity, and retain it in the finalized pull
request only when that run is launched and monitored. Inspect the staged file
list with `git diff --cached --name-only` before committing and fail closed if
any YAML is outside the minimal closure. Record the primary config path, commit
SHA, pull request URL, and launched run identity in the experiment report.

Require a remote node that is `READY`, `HEALTHY`, and Spot/preemptible when requested. Treat a matching TPU name as only a candidate and run the occupancy helper from `query-monitor-gcp-tpus`. Leave a healthy `kristine` or current-user workload alone. Standing user authorization permits terminating a current-user ELF process only if it is proven stuck or race-blocking the authorized run on that exact `kristine` TPU: record every worker's owner, PID, full command, run identity, lock, and stale-progress evidence; TERM it; revalidate before any KILL escalation; and require all workers to report idle afterward. Never apply this exception to a foreign, unknown, non-ELF, or healthy holder. Only during the otherwise guarded candidate-claim step on a `kristine` TPU may the helper terminate a positively identified foreign, non-`kristine` VFIO holder; never apply that claim permission to an unknown holder, during the final launch gate, or on a TPU whose name lacks `kristine`. If a run is owned by somebody else on a non-`kristine` TPU, never edit, stop, touch, or interrupt it.

When occupancy is found, record each holder's owner, command, and run identity before deciding. If it belongs to a healthy active selected ELF run, leave it running and switch to monitoring. The only current-user exception is the verified stuck/race protocol above. On a `kristine` TPU, a positively identified foreign VFIO holder may be reclaimed through the guarded claim workflow. If a run is owned by somebody else on a non-`kristine` TPU, never edit, stop, touch, or interrupt it.

For v6e, estimate aggregate peak HBM for parameters, optimizer state, gradients, activations, and compiler buffers. Require aggregate HBM to be at least twice the estimate. Use 32 GB HBM per v6e chip.

## Enforce storage locality

Derive the TPU region by removing the final zone suffix. Apply all of these gates:

- Create the canonical source snapshot under `/kmh-nfs-ssd-us-mount/staging/kristine/elf/<run-id>`, then allow one completed copy from that snapshot to node-local storage on an authorized `kristine` TPU. After the copy, never train from, mount, stream, repeatedly synchronize, or otherwise read the NFS path during the workload.
- Put staged datasets under `/home/$USER/elf-data/` on every worker. First verify whether the selected region's `kristine` bucket path contains a complete dataset; reuse a valid node-local copy or stage that bucket source. A direct Hugging Face download is allowed only when the matching regional `kristine` dataset path is absent or fails integrity verification.
- Keep source, logs, caches, outputs, and checkpoints on each worker's local root disk under `/home/$USER/elf-runs/`.
- A single finalized checkpoint may be copied once between regional buckets when the optimal selected TPU requires it. Verify the source completion marker, byte count, and SHA-256 before copying, then verify the destination object and node-local file against that same evidence. This exception never applies to datasets.
- Inspect every effective CONFIG/config file before launch. For each `gs://` data, resume, checkpoint, output, or artifact URI, require the bucket's reported location and service-account mapping to equal the TPU region. Never use a default bucket fallback.
- Check free space on every worker before download. Budget the complete dataset, model/tokenizer caches, temporary files, logs, and at least two checkpoints.
- If disk capacity is insufficient, first prove that the selected run's complete verified dataset is absent. Only then may cleanup remove current-user-owned, inactive, explicitly irrelevant, regenerable staging/download/cache artifacts. Record every target before removal; never remove checkpoints, outputs, source snapshots, credentials, or any other user's files.

Use `scripts/preflight_remote_elf.sh` from the repository root for the remote-state, path, process, and disk checks. Read the script before running it. Also require the launch preflight to reject an existing `/tmp/tpu_logs` that is not writable by the remote ELF user; record its mode and ownership instead of discovering the conflict during distributed initialization.

For the configured node-local `output_dir`, first validate its exact parent is under `/home/$USER/elf-runs/`. The launcher must idempotently create only that parent on every worker before checking its ownership and writability; it must never create the run output itself. Require the exact `output_dir` to remain absent as the independent freshness gate—an existing parent is expected and does not authorize reuse. If parent setup fails, preserve the zero-step attempt, use a fresh retry identity, and verify no trainer, run output, or checkpoint exists before retrying.

## Stage source on NFS, then copy it to the VM

Run `bash tpu_scripts/run_staging.sh <run-id>` from the ELF repository. Require its output path to be below `/kmh-nfs-ssd-us-mount/staging/kristine/elf/`. This snapshot includes the current worktree and uncommitted source while excluding `.git`, secrets, experiment logs, outputs, caches, and virtual environments. Never overwrite or mutate an existing run snapshot.

Copy that exact NFS snapshot to every TPU worker with `gcloud ... tpu-vm scp --worker=all`, placing it below `/home/$USER/elf-runs/source/<run-id>`. When disabling SSH config lookup and requiring legacy SCP, pass the flags exactly as `--scp-flag=-F --scp-flag=/dev/null --scp-flag=-O`. Each repeated `--scp-flag` forwards one argv value, so bundling `--scp-flag="-F /dev/null"` fails to provide `-F` and its path separately; `-O` avoids the modern SFTP transport on legacy TPU images. Require exit status zero, then verify `train.py`, the selected CONFIG, and the expected source size or hash on every worker before launch.

The one-time copy from `/kmh-nfs-ssd-us-mount` is allowed even when the control host and TPU are in different zones or regions. On the TPU, do not `cd` into, import from, or write to `/kmh-nfs-ssd-us-mount` after the copy. Set `PYTHONPATH` only to the VM-local source directory.

## Prepare data on every worker

Never copy a dataset across regions. First inspect the selected TPU region's `kristine` bucket path; when it is complete and verified, stage it to an explicit node-local `local_dir` on every worker (or reuse the verified node-local copy). Redownload from Hugging Face only when that matching regional `kristine` path is absent or fails integrity verification. After completion, verify `state.json`, `dataset_info.json`, total size, and free disk space on every worker.

Set the ELF `data_path` override to the downloaded directory. The OpenWebText dataset in this repository is a `save_to_disk` Arrow snapshot, so `utils.data_utils.load_dataset_split` must load that directory with `datasets.load_from_disk`.

## Gate input-pipeline throughput

Before promoting a full run, audit the exact immutable snapshot and run a bounded throughput smoke. Require host collation, preparation, and prefetch payloads to carry only linear `[batch, sequence]` masks such as `attention_mask` and `cond_seq_mask`; never materialize or transport a quadratic `[batch, sequence, sequence]` attention mask. Reconstruct every quadratic mask inside the compiled train or evaluation step on the TPU, and require a focused fixture to prove both the linear host payload and mask-semantic parity.

Measure actual examples processed: `examples_per_second = (training_loop_steps_in_interval * global_batch_size) / interval_wall_seconds`, where `global_batch_size` is the global microbatch consumed by each training-loop step. Never multiply every loop step by `grad_accum_steps`. For a complete optimizer-update interval only, the equivalent numerator is `effective_batch_size = global_batch_size * grad_accum_steps`, and the denominator must span that full accumulation window. Exclude compilation, evaluation, profiling, checkpointing, and cache-warmup intervals; compare several consecutive steady-state steps against an accepted benchmark with the same model, sequence length, precision, backend/tiles, topology, and effective batch. Record the benchmark and tolerance in the experiment report. Treat a major unexplained regression as a failed throughput gate: preserve any scientific smoke result, block full promotion, fix the input path, and rerun under a distinct immutable identity.

## Launch

Immediately before opening the foreground fan-out, after all source, runtime, and data setup, rerun the occupancy helper on every worker and inspect both `/dev/vfio/*` and `/tmp/libtpu_lockfile`. Reject an unheld lockfile as `stale_libtpu_lock`; libtpu can refuse initialization from the file's existence even when `fuser` reports no live holder. This is a fresh fail-closed gate: require every worker to remain idle with no lockfile at the canonical path and never reuse the initial preflight result. If any holder, stale lock, or conflicting setup activity appeared, start no worker, terminate or move nothing in this final gate, and preserve the collision as a zero-step failed attempt with the worker, PID or lock metadata, numeric UID, and command when available. On a `kristine` TPU, return to the separate guarded candidate-claim workflow before any retry. If a run is owned by somebody else on a non-`kristine` TPU, never edit, stop, touch, or interrupt it.

When an external controller is confirmed to relaunch the same explicitly authorized foreign job on a `kristine` TPU during the preflight-to-backend-open interval, the separate guarded candidate-claim workflow may remain active only until ELF acquires the accelerator. Keep it exact-resource, exact-owner, exact-process, exact-command-fragment, bounded, and fail-closed. This claim stays on `kristine` TPUs. If a run is owned by somebody else on a non-`kristine` TPU, never edit, stop, touch, or interrupt it.

Launch one foreground SSH fan-out command with `--worker=all`; preserve its local session for monitoring. Let `jax.distributed.initialize()` discover the Cloud TPU workers. Do not hard-code `JAX_PROCESS_COUNT` or assume eight workers.

Set `JAX_PLATFORMS=tpu`, `CUDA_VISIBLE_DEVICES=''`, `HF_HOME` to node-local storage, and a unique node-local `output_dir`. Pass `--config_override epochs=<count>`, `data_path=<node-local-path>`, `output_dir=<node-local-path>`, and `resume=None` for a fresh run. Keep the configured seed unless the user supplies another.

Start W&B only on TPU worker zero before `jax.distributed.initialize()`, but identify that worker from launcher-provided VM metadata rather than any JAX API. During `wandb.init`, temporarily expose only `JAX_PLATFORMS=cpu` to W&B subprocesses and disable W&B system-stat collection; restore the trainer's TPU platform before forming the JAX runtime. Keep ELF application metrics enabled. This prevents W&B hardware helpers from opening a second libtpu client and joining a multi-host launch group with a conflicting launch ID.

For every exact-checkpoint evaluation, resolve the canonical source training run from the verified checkpoint ancestry and set `wandb_group` to that exact source run ID before launch. Do not infer the group from an evaluation display name when checkpoint ancestry is available. Keep distinct W&B run IDs and display names for checkpoint steps, sampling policies, retries, and hardware, but place every evaluation of the same source training run in the same group. Before launch, verify the effective config contains that group; after W&B starts, read the created run back and verify its group matches. Record the group in the experiment report. Changing existing W&B runs is a separate post-hoc mutation and requires an explicit user request naming the intended run set.

If first-step libtpu reports `An unexpected peer shows up in the launch group with a different launch id`, count timestamped libtpu clients on every worker and correlate them with W&B startup. More than one client on a worker is a subprocess/duplicate-runtime failure; fix the extra client before retrying. If every worker has exactly one intended client, treat libtpu's multi-controller model/XLA nondeterminism branch as the remaining cause. Recover on a single-host topology when possible, scaling global microbatch with device count so per-chip batch and `global_batch_size * grad_accum_steps` stay fixed. Require a new immutable retry identity and reapply the HBM gate.

Do not report a launch as successful until every worker reaches distributed initialization and worker 0 reports the model, effective data path, output path, and device count. A training launch additionally requires its first completed training step. An exact evaluation launch instead requires confirmation of the exact restored checkpoint plus its first useful evaluation progress event, such as validation or generation starting. A process merely existing is only `STARTING`.

For every launched experiment, use the repository's `report-experiment-logs` skill to create a new uniquely named report under `experiment_log/`. Never overwrite prior records.

## Install preemption-aware monitoring and recovery

After the first completed training step, or after the first useful exact-evaluation progress event, install one recurring `tpu_scripts/watch_elf_run.sh` invocation for the run at an interval of at most 30 minutes. Pass its optional final workload role explicitly: `training` for ordinary runs, `evaluation` for exact-checkpoint evaluators, and `checkpointing` for runs whose primary deliverable is a checkpoint. Resolve and pin absolute executable paths through `ELF_MONITOR_GCLOUD`, `ELF_MONITOR_PYTHON`, and `ELF_MONITOR_CODEX`; require the selected Python to import `wandb`. Run the exact installed command once under `env -i HOME=<user-home> SHELL=/bin/bash PATH=/usr/local/bin:/usr/bin:/bin` and reject the monitor if any tool, import, cloud describe, W&B lookup, or recovery executable fails. Classify missing monitor executables, imports, or transport as monitor infrastructure failure, never TPU loss, trainer failure, or Spot preemption; do not start recovery until the pinned `gcloud` completes a direct exact-resource query.

For runs with scheduled generation evaluation, set `ELF_MONITOR_EVAL_INTERVAL_STEPS` to the configured training-loop interval, `ELF_MONITOR_EVAL_GRACE_STEPS` to a bounded post-boundary allowance, and `ELF_MONITOR_EXPECTED_GENERATION_SAMPLES` to the exact requested count. Require the monitor to reconcile `validation_metrics.jsonl`, generation `metrics.jsonl`, and the generated JSONL row count. Report completed PPL/MAUVE separately from an evaluation still in progress. Treat an exact-count, full-length whitespace-only output as `collapsed_step_<n>` and send one evaluation alert without restarting a healthy trainer; treat missing or wrong-count artifacts after the grace window as evaluation alerts, not TPU-preemption recovery triggers.

Treat the ELF training interpreter and the Cloud SDK interpreter as separate compatibility domains. Never blindly set `CLOUDSDK_PYTHON` to `ELF_RUNTIME_PYTHON`, and do not assume the TPU image's system Python or the SDK's bundled default is compatible. On the exact worker image, preflight the exact `gcloud storage` command shape used by checkpoint mirroring with each candidate interpreter; run the same subcommand and flags against a harmless run-scoped probe while exercising authentication and the intended regional bucket or prefix rather than accepting `--help` alone. Legacy Cloud SDK 127 imports the removed `imp` module and fails under Python 3.12, while some refreshed SDK and system Python 3.8 combinations fail in dependencies and require the ELF Python 3.11 runtime. Fail closed and select only an explicitly verified `CLOUDSDK_PYTHON`, or leave it unset only after the bundled SDK default passes the same probe. Record the Cloud SDK version, resolved Python version/path, probe command, and result. After each finalized checkpoint, validate the canonical `OUTPUT_DIR/checkpoint_mirror.pid`, its live non-zombie state, exact script/output/GCS/run cmdline identity, and exactly one independent matching process-tree root; ignore short-lived matching descendants rather than treating raw `pgrep` count as daemon count. Require the local completion marker to match the finalized checkpoint, and do not accept a running trainer alone as durability evidence. If only the mirror exits with a Cloud CLI Python/import error, keep the healthy trainer running, verify the local checkpoint, rerun the exact compatibility probe, restart exactly one mirror with the verified Cloud SDK interpreter, and require the completion marker before clearing the alert.

Avoid aliasing checkpoint cadence with monitor cadence. Include the finalized checkpoint's modification epoch in remote status and configure a short bounded `ELF_MONITOR_CHECKPOINT_MIRROR_GRACE_SECONDS` window (180 seconds by default). Report a missing marker inside that window as `pending_grace` without incrementing infrastructure failures; continue to call it unverified. Once the checkpoint is older than the grace, classify the missing marker as `checkpoint_mirror_pending` normally. A grace must never accept a marker for an older checkpoint or hide a stale/dead mirror helper.

At throughput-gate and monitoring checks, report examples/second using the loop-step/global-microbatch definition above, identify compile/evaluation/checkpoint intervals, and compare steady-state values with the accepted benchmark. Alert on a sustained major regression and never promote the full run from steps/second alone.

Use direct TPU API state as the primary infrastructure signal. Classify an exact-resource `NOT_FOUND`, `PREEMPTED`, or `DELETING` response as TPU loss; do not let a later W&B `crashed` state overwrite that classification. Classify missing executables, authentication errors, and transport failures as monitor failures rather than preemptions. Use W&B and the worker log as independent progress evidence, not substitutes for direct TPU state. Resume at the checkpoint's deterministic distributed-sampler batch offset; never load, collate, and discard every earlier batch merely to restore iterator position. During a legacy resume, distinguish synchronous dataloader replay from a stall: a live trainer with increasing CPU/page-fault counters, fresh libtpu heartbeats, and successful local W&B filestream requests remains `STARTING` even if no new training metric exists yet. Never launch a duplicate recovery from W&B's `crashed` label alone in that state.

Before any preemption recovery, capacity query, or checkpoint localization, reconcile the precursor's complete lineage against all experiment reports, every active installed monitor and recovery orchestrator, and authenticated read-only W&B state. Match scientific configuration, run/retry identifiers, resume ancestry and checkpoint step, W&B run ID, timestamps, current state, and latest metric step; do not assume the report named by the alert is still canonical. If a newer active successor exists, stop recovery before checkpoint copying, capacity acquisition, staging, or launch. Retire only the obsolete predecessor's monitor and recovery trigger, preserve the successor's monitor, trainer, artifacts, and capacity, and record the reconciliation in both reports. Never create a duplicate full run from an older checkpoint. Proceed only after proving that no active successor or duplicate exists and selecting one canonical lineage head.

On confirmed TPU loss, keep one recovery orchestrator and follow this sequence:

1. Record the last W&B/log step and verify the newest finalized regional checkpoint and its success marker. Treat all deleted-node artifacts as unavailable.
2. Run `ELF_TPU_INITIALIZE_MISSING=0 bash tpu_scripts/check_tpus.sh he-vision-group`; select only an authorized idle candidate from the final `AVAILABLE` table, then directly describe it and run the occupancy helper.
3. Initialize and revalidate only the selected candidate when its ELF runtime is missing. If no candidate exists, keep the filtered `check_tpus.sh` audit active instead of provisioning a TPU. For a confirmed v6e loss with no matching v6e capacity, an existing `AVAILABLE` v5p-8, v5p-16, or v5p-32 is an approved fallback only when the checkpoint, dataset, and future outputs remain in its region. Use a fresh retry identity, reapply the compatibility/HBM/throughput gates, and document any parameter-free backend substitution required for v5p; never silently change model hyperparameters.
4. Create a distinct retry identity, output path, mirror prefix, W&B run, and experiment report, but populate the retry's immutable snapshot from the precursor's byte-identical source and effective configuration rather than the current mutable worktree. On every recovery, re-push that snapshot and selected configuration to every replacement worker before localizing the checkpoint or opening the TPU runtime; never rely on files from a prior TPU. Resume training only from a verified compatible checkpoint; when none exists, a training run may restart the exact scientific configuration from step zero and must record why. An exact-checkpoint evaluation must stop when its exact compatible checkpoint cannot be verified; never substitute another step or restart it from step zero.
5. Preserve one foreground worker fan-out, verify distributed initialization and the first completed step, install and minimal-environment-test the retry monitor, then continue checks through completion or another recovery.
